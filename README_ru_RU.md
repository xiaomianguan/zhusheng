# zhusheng

![slop badge](.github/assets/slop_badge.webp)

[简体中文](README.md) | [繁體中文](README_zh_TW.md) | [English](README_en_US.md) | [Polski](README_pl_PL.md) | Русский | [Svenska](README_sv_SE.md)

**zhusheng** возвращает общесистемное доверие TLS/HTTPS на старых устройствах с
Android (**4.0 - 6.0**, API 14 - 23): он загружает официальные корневые
сертификаты, публикуемые крупнейшими поставщиками TLS/SSL, и устанавливает их в
хранилища сертификатов Android.

Старые устройства поставляются с устаревшим набором доверенных корней. Когда сайт
обслуживает удостоверяющий центр, которого не существовало (или которому не
доверяли) на момент выпуска устройства - самый известный пример это
**Let's Encrypt** - любой запрос HTTPS падает с ошибкой сертификата, и устройство
«не может нормально выходить в интернет». zhusheng исправляет это, устанавливая
недостающие корни.

* Работает на **всех архитектурах** (приложение написано на чистой Java, без
  нативного кода).
* Работает на **Android с 4.0 по 6.0**.
* Использует только **штатные компоненты интерфейса Android** - без AndroidX и
  без сторонних библиотек.

## Как это работает

1. **Загрузка.** Выберите нужных поставщиков (или оставьте рекомендуемый набор) и
   нажмите *Скачать выбранные*. Сертификаты загружаются с официальных точек
   доступа CA, перечисленных ниже.
2. **Установка.** Есть два режима:
   * **Системное хранилище (нужен root)** - сертификаты записываются в виде файлов
     PEM в `/system/etc/security/cacerts/<subject_hash>.<n>`, точно так же, как
     предустановленные корни, после чего `/system` снова монтируется только для
     чтения. Изменения вступают в силу после перезагрузки. Так им доверяют *все*
     приложения.
   * **Пользовательское хранилище (без root)** - сертификаты ставятся через
     системный установщик сертификатов Android
     (`KeyChain.createInstallIntent`). В версиях Android **ниже 7.0**
     сертификаты из пользовательского хранилища считаются доверенными в масштабе
     всей системы, так что это тоже исправляет HTTPS во всех приложениях и без
     root. Кнопка сначала спрашивает, как должны проходить подтверждения
     установщика, и предлагает три способа (`UserInstallMode`; выбор
     запоминается и предлагается в следующий раз):
     * **один запрос на весь набор** - весь набор сначала предлагается установщику
       **одним** intent: это пакет учётных данных (credentials bundle) с одной
       записью `CACERT_<n>` на сертификат
       (`CertInstaller.userStoreBulkInstallIntent`). Понимающий его установщик
       добавляет все корни за один проход; некоторые сборки 4.x читают пакет и
       молча его игнорируют, и тогда приложение возвращается к одному сертификату
       на окно;
     * **один запрос на сертификат** - пакет не пробуется вообще, поэтому
       установщик спрашивает об одном сертификате за раз. Медленнее первого
       способа, но ведёт себя одинаково в любом установщике;
     * **подтверждать запросы автоматически** - тот же прогон, что и первый
       способ, но запросы подтверждает **служба автоподтверждения**.

     Сертификаты, которым устройство **уже доверяет, пропускаются**, а дубликаты
     между источниками отбрасываются (`TrustedRoots`), поэтому повторный запуск -
     или продолжение прерванной установки - уже не требует ничего подтверждать.

     **Служба автоподтверждения** необязательна и требует **Android 4.1 или
     новее**. Приложение не вправе включить собственную службу специальных
     возможностей - это делает только пользователь в системных настройках
     специальных возможностей, и поэтому приложение объясняет, что это за служба,
     и называет пункт, который нужно найти, прежде чем открыть эту страницу. Она
     также предупреждает, что служба работает, быстро проходя один экран за
     другим, поэтому во время прогона экран может мигать, и указывает тем, кому
     мешает мигающий свет, на два способа с подтверждением вручную. Так делает и
     пункт меню *Автоподтверждение установки*, и выбор автоматического способа
     выше, когда служба ещё не включена; во втором случае установка запускается
     сама, как только пользователь вернётся из настроек. Пока идёт
     прогон, начатый этим приложением, служба нажимает кнопку *OK* в окнах
     установщика, а при удалении - строки списка сертификатов; вне такого прогона
     она не делает ничего, а два способа с подтверждением вручную никогда не дают
     ей команду стартовать. В Android 4.0 среда специальных возможностей вообще не
     умеет нажимать кнопку (`performAction(ACTION_CLICK)` появилось вместе с
     `View.performAccessibilityAction` в 4.1), поэтому на устройстве с 4.0 запросы
     подтверждаются вручную.

3. **Удаление.** Оба хранилища можно снова очистить, так что установку можно
   отменить без второго устройства и без сброса к заводским настройкам:
   * **Системное хранилище (root)** — удаляет только те файлы, которые добавило это
     приложение. Приложение записывает имя каждого скопированного файла
     (`system-installed.txt` в своём приватном каталоге `files`) и перед удалением
     сверяет содержимое файла с сертификатом: корень, поставленный с устройством, и
     тот же корень из пакета могут быть одними и теми же байтами, по одному
     хранилищу их не различить, а поставленный корень удалять нельзя.
   * **Пользовательское хранилище** — в нём нет API для удаления сертификата,
     поэтому **3b. Удалить из пользовательского хранилища** спрашивает, каким из
     трёх способов это сделать, — так же, как 2b спрашивает о подтверждении
     установки (`UserRemoveMode`; выбор тоже запоминается на следующий раз):
     * **Удалить файлы с помощью root** — файлы в `/data/misc/user/0/cacerts-added`
       (в старых версиях `/data/misc/keychain/cacerts-added`) читаются напрямую.
       Файл удаляется только тогда, когда его содержимое — один из загруженных
       сертификатов. Это единственный способ, которому нужен root; на устройстве
       без root он показан серым и подписан как недоступный, поэтому выбрать его
       нельзя.
     * **Удалить вручную в настройках** — открывается список сертификатов
       в системных настройках, и каждый сертификат вы удаляете там сами: нажмите
       его строку, затем *Удалить*, затем подтвердите. Приложение ничего не удаляет,
       и этот способ не требует root. В окне перечислены шаги и есть кнопка для
       перехода на этот экран; снимки экрана для этой инструкции ещё появятся.
     * **Удалить автоматически (служба спец. возможностей)** — тот же список, но
       за дело берётся служба автоподтверждения (см. ниже).

   Способы, которые действительно что-то удаляют, — 3a и способ с root в 3b —
   сначала спрашивают подтверждение, и обоим нужен root: в пользовательском
   хранилище потому, что нет API, а не из-за способа записи.

   Третий способ оставляет удаление **службе автоподтверждения**: приложение
   открывает тот же список сертификатов и передаёт
   службе имена загруженных сертификатов, а она нажимает строку каждого из них,
   кнопку *Удалить* на открывшемся экране сведений и отвечает на появляющийся
   вопрос. Она касается только строк, имя которых совпадает с одним из этих
   сертификатов, и останавливается, как только приложение снова окажется впереди
   — список опять принадлежит пользователю. Для этого нужна та же включённая
   служба, и она проходит по экрану настроек той версии, на которой работает; в
   Android 5.0 и 6.0 это нажатие строки, кнопка *Удалить* под сведениями о
   сертификате и *Да*. Если служба не включена, приложение сначала объясняет её и
   даёт кнопку, открывающую эту страницу, а по возвращении спрашивает об удалении
   ещё раз.

   Каждый запуск скрипта от имени root - и установки, и удаления в обоих
   хранилищах (2a, 3a и способ root в 3b) - заканчивается окном, в котором вывод
   скрипта цитируется ровно таким, каким он вернулся (именно этот вывод и должен
   попадать в отчёт об ошибке), а под ним разбираются распознанные маркеры на том
   языке, на который переключено приложение (`ScriptNotes`): `ZHUSHENG_COPIED=`,
   `ZHUSHENG_REMOVED=`, `ZHUSHENG_DEDUPED=`, `ZHUSHENG_DONE`, а также строки
   `no system-installed.txt`, `could not write`, `command timed out` и
   `exec failed`. Пояснения идут в том порядке, в котором маркеры встречаются в
   выводе, маркер, напечатанный дважды, поясняется один раз, а всё, чего
   приложение не распознаёт, всё равно цитируется как есть. Пустой вывод получает
   вместо этого единственное пояснение, которое тогда важно: скрипт ничего не
   напечатал - именно так выглядит отклонённый запрос на root. (На устройстве без
   root до этого окна дело не доходит: 2a и 3a сообщают, что root отсутствует, а
   способ root в 3b показан серым.)

На **Android 7.0 (API 24) и новее** система больше не доверяет сертификатам,
установленным пользователем, для приложений, ориентированных на 7.0 или новее,
поэтому режим *пользовательского хранилища* там не действует для большинства
приложений; режим *системного хранилища* может ещё работать, но для него нужен
root, а версии выше 6.0 выходят за рамки того, что zhusheng официально
поддерживает (в следующих выпусках Android системное хранилище сертификатов
менялось ещё сильнее). Приложение объясняет это один раз, при **первом запуске**:
`LegacyNotice` вызывается в конце `onCreate()`, а флаг `legacy_notice_shown`
сохраняется в `SharedPreferences`.

Имена файлов в системном хранилище строятся по значению OpenSSL
`x509 -subject_hash_old` (MD5 от субъекта в кодировке DER); приложение
воспроизводит этот алгоритм на Java (`HashUtils.subjectHashOld`). Совпадение с
OpenSSL проверено побайтово.

**Mozilla CA Bundle** - универсальное решение: он содержит корни всех крупных CA

чинит подавляющее большинство недоступных сайтов.
### Безопасность загрузки

Поскольку сломано как раз хранилище доверия устройства, полностью проверенное
HTTPS-соединение с этими точками доступа может не удаться (например,
`letsencrypt.org` обслуживается сертификатом Let's Encrypt). Устройство на
Android 4.0 вообще не может выполнить требуемое этими узлами рукопожатие TLS - а
именно для таких устройств и сделана эта программа - поэтому загрузка
последовательно отступает к обычному HTTP:

1. сначала пробует загрузку по HTTPS с **обычной проверкой**, и только если она
   не удалась,
2. повторяет попытку, принимая любой сертификат сервера,
3. повторяет попытку по тому же адресу через **обычный HTTP**, и наконец
4. берёт **копию по обычному HTTP**, которую несёт сам источник, - для узлов,
   отвечающих только по https (фиксированный снимок официального файла в Internet
   Archive).

Доверие обеспечивает не это, а проверка содержимого после загрузки, корень за
корнем:

* каждый сертификат должен быть **самоподписанным корнем** (subject == issuer, а
  подпись проверяется его же ключом),
* источник с одним сертификатом сверяется с **закреплённым отпечатком SHA-256**,
  а
* пакет сверяется с **отпечатками всех корней, которые в нём ожидаются**
  (`KnownRoots`), поэтому содержимое, загруженное по обычному HTTP, не может
  протащить собственный корень.

Подделанная загрузка поэтому не может незаметно установить подложный корень.

## Темы

Приложение предлагает три темы и две цветовые схемы, которые выбираются кнопкой
**Тема** на верхней панели; выбор запоминается в `SharedPreferences`. **На
Android 5.0 и новее по умолчанию используется Material** (он подходит окружающей
системе); на Android 4.x стартует Holo, а устройства Smartisan стартуют с **темой
устройства** (`LaoLuo`), чтобы приложение открывалось в фирменном оформлении
производителя на той прошивке, для которой оно сделано. Как только тема выбрана
осознанно, этот выбор всегда побеждает.

| Вариант | API 14 - 20 (4.0 - 4.4W) | API 21+ (5.0 - 6.0) |
| --- | --- | --- |
| **Holo** | `Theme.Holo.Light.DarkActionBar` | `Theme.Holo.Light.DarkActionBar` |
| **Material** | недоступна (затемнена) | `Theme.Material.Light.DarkActionBar` |
| **Системная** | `Theme.DeviceDefault.Light.DarkActionBar` | `Theme.DeviceDefault.Light.DarkActionBar` |

* **Holo** - исходная тема, доступна во всех поддерживаемых версиях, но по
  умолчанию используется только на Android 4.x.
* **Material** использует компоненты Material Design 1 из фреймворка, поэтому
  доступна только на Android 5.0+, где она и **является темой по умолчанию**. На
  Android 4.x этот вариант **затемнён** в списке, а под ним есть пояснение, почему
  так, вместо тихого отката к Holo.
* **Системная** использует тему, которую предоставляет производитель устройства
  (TouchWiz, Sense, MIUI, ...), через `Theme.DeviceDefault`.

### Цветовая схема

Каждая тема бывает **светлой** и **тёмной**:

* **Светлая** (по умолчанию) использует вариант `DarkActionBar` - светлая область
  содержимого с тёмной панелью действий - то есть исходный вид приложения.
* **Тёмная** использует полностью тёмный вариант той же темы (`Theme.Holo`,
  `Theme.Material`, `Theme.DeviceDefault`).

Цвета собственных поверхностей приложения (фон, основной текст, второстепенный
текст, разделитель списка) объявлены атрибутами темы `zsBackground`,
`zsTextPrimary`, `zsTextSecondary` и `zsDivider` (см. `res/values/attrs.xml`),
поэтому в тёмной схеме область содержимого не остаётся белой. Шесть базовых тем
задают светлые значения; тёмная схема переопределяет их через
`ThemeOverlay.Zhusheng.Scheme.Dark` в `Theme.applyStyle()`.

### Цвета

В окне темы есть и выбор цвета. Первый образец (по умолчанию) означает **оставить
цвет самой темы**, поэтому без выбора вид остаётся точно таким, как был; образец
по умолчанию у Holo показывает бирюзовый, которым тема сама и рисует. У выбранного
образца посередине галочка: белая в светлой схеме и чёрная в тёмной, где оттенки
200 слишком бледные для белой галочки. Единственное исключение - первый,
«по умолчанию», образец: он носит цвет самой темы, поэтому его галочка выбирается
по яркости. Строка с версией под подзаголовком (`device_info`) - единственный
элемент приложения, который всегда носит акцентный цвет, поэтому без выбора она
использует цвет темы и не спорит с флажками рядом.

| Тема | Цвета | Где применяются |
| --- | --- | --- |
| **Holo** | акцент (4 цвета Holo) | всё, что тема рисует своим бирюзовым: флажки списка, переключатели и галочки в окне, индикатор выполнения, ссылки, заголовок окна и разделитель под ним, кнопки окна, синяя линия внизу тёмной панели действий и строка версии под подзаголовком (для части с покадровой раскраской нужен API 21+) |
| **Material** | основной (10 цветов Material) + акцент (10) | основной цвет задаёт панель действий и строку состояния **светлой** схемы (тёмная всегда сохраняет свои тёмную панель и строку состояния), акцент задаёт флажки, индикатор выполнения, кнопки окна, строку версии под подзаголовком и так далее |
| **Системная** | нет | цвета берутся из темы производителя |
* Цвета **Material** накладываются через наложения темы
  (`android:colorPrimary` / `colorPrimaryDark` / `colorAccent` /
  `colorControlActivated`), определённые в `res/values-v21/color_overlays.xml` и
  накладываемые на тему методом `AppColors.applyTheme()` после `setTheme()` и до
  `super.onCreate()`. Именно так Material сам определяет эти цвета, поэтому за
  ними следуют все виджеты.
* **Акцент** у **Material** следует цветовой схеме точно так же, как акцент самой
  темы: светлая схема использует оттенки 500, а тёмная - **оттенки 200** (Material
  сам так делает: его акцент - это deep teal 500 `#009688` в светлой теме и
  deep teal 200 `#80CBC4` в тёмной). **Основной цвет применяется только в светлой
  схеме**: тёмная тема сохраняет тёмную панель действий и чёрную строку состояния,
  как это делает собственная тёмная тема Material и как советует Material Design
  (панель в основном цвете слепила бы на тёмном содержимом). Поэтому выбранный
  основной цвет никогда не перекрашивает тёмную панель - строка остаётся рабочей,
  и выбор снова действует в светлой схеме. В строке акцента есть один вариант,
  которого нет в строке основного цвета, - **чёрный / белый** перед зелёным:
  чёрный в светлой схеме, белый в тёмной, поэтому он виден в обеих. Светлая схема
  сохраняет оттенки 500, поэтому выглядит точно как раньше. Выбор хранится как
  цвет, который был на экране в момент выбора, поэтому один и тот же выбор
  читается то как 500, то как 200; `AppColors.indexOfColor()` ищет его в обеих
  палитрах.
* У **Holo** нет атрибута акцента, да и виджеты фреймворка его не читают, поэтому
  акцент применяется по одному представлению: `setButtonTintList()` для флажков и
  переключателей, `setProgressTintList()` для индикатора выполнения, так же для
  элементов внутри окна (включая строки списка одиночного выбора), а обычный
  цвет - для заголовка окна, разделителя под ним, кнопок окна, ссылок и строки
  версии под подзаголовком. Строка версии - единственный элемент, который
  сохраняет акцент даже при варианте по умолчанию: тогда она носит цвет самой темы
  и потому всегда совпадает с флажками. **Сама панель действий остаётся чёрной**,
  как в теме, и акцентным цветом покрывается только синяя линия, которую тёмная
  схема рисует по её нижнему краю. В Android 4.x нет API раскраски, поэтому там за
  акцентом следует только текст; список сообщает об этом ниже.
* В палитре Holo **нет** бирюзового самой темы (`#0099CC`): именно его обозначает
  вариант по умолчанию, поэтому они были бы неразличимы. По той же причине палитра
  акцента Material не включает teal (`#009688`) - это акцент, которым Material сам
  рисует свои виджеты, - и вместо него добавляет вариант **чёрный / белый**,
  которого нет в строке основного цвета, поэтому в обеих строках по десять цветов
  (строка акцента меняет teal на чёрный / белый; teal остаётся допустимым основным
  цветом).

Определения тем лежат в `res/values/styles.xml`, а переопределения для Android 5.0+
- в `res/values-v21/styles.xml`. Активная тема применяется в
`MainActivity.onCreate` через `setTheme()`, до создания представления содержимого.
Доступна ли тема на текущем устройстве, решает `AppThemes.isAvailable()`; `get()`
возвращается к Holo, если сохранённая тема недоступна (например, после
восстановления копии с устройства 5.0+ на 4.x).

Смена темы, цветовой схемы или цвета перезапускает активность **новым намерением**
(а не через `recreate()`): Holo и Material используют разные реализации панели
действий, и `recreate()` заставляет фреймворк восстановить сохранённое состояние
одной панели в другой, что приводит к `ClassCastException`
(`ActionBarView$SavedState cannot be cast to Toolbar$SavedState`) и падению
приложения.

## Интерфейс

Главный экран - это одна прокручиваемая страница: столбец представлений, из которых
гибким является список источников. `PageScrollView` отдаёт этому списку место,
оставшееся на странице, - экран без заголовка над ним, полосы прогресса и строки
состояния под ним и кнопок под ними, - а когда места меньше, чем просит список, то
его минимум, и тогда прокручивается сам список, а всё вокруг остаётся на месте.
Сама страница прокручивается только тогда, когда этого места меньше минимума, и
лишь на тот небольшой излишек. Именно это и позволяет `PageListView`: он сообщает
высоту всех своих строк, а не той единственной, до которой платформа измеряет
список внутри прокручиваемой страницы, и сам вычисляет свой минимум - две строки -
по высоте, которая окажется у строки. Полоса прокрутки списка остаётся на экране,
поэтому строка, заканчивающаяся ровно на его нижнем крае, - не единственный признак
того, что ниже есть ещё источники.

У страницы есть отступ только слева и справа, а вертикальный отступ принадлежит
столбцу внутри. `ScrollView` ограничивает прокрутку высотой своего содержимого за
вычетом собственных отступов, поэтому вертикальный отступ страницы - это место, в
которое содержимое никогда не прокрутится: оно стоит на месте сверху и снизу
области прокрутки, а содержимое проезжает за ним, и это выглядит так, будто
страница обрывается с обоих концов.

На верхней панели - кнопка **Тема**, а в меню за ней: выбор языка, сайт проекта,
GitHub, окно *О программе* и *Автоподтверждение установки* (с Android 4.1, где
платформа спец. возможностей умеет нажимать кнопку).

## Локализация

Интерфейс доступен на шести языках: **简体中文**, **繁體中文**, **English**,
**Polski**, **Русский** и **Svenska**.

* По умолчанию приложение **следует языку системы**: Android выбирает подходящий
  каталог `res/values-*`, а язык вне этих шести обслуживается каталогом
  `res/values` (английский). `zh-CN` использует `res/values-zh-rCN` (упрощённый),
  `zh-TW` использует `res/values-zh-rTW` (традиционный), любой другой китайский
  язык использует `res/values-zh` (упрощённый), а `pl`, `ru` и `sv` используют
  `res/values-pl`, `res/values-ru` и `res/values-sv`.
* Пункт **Язык** в меню позволяет это переопределить: можно выбрать *Как в
  системе* и шесть языков, всегда в одном и том же порядке: 简体中文, 繁體中文,
  English, Polski, Русский, Svenska. Выбор сохраняется в `SharedPreferences` и
  применяется в `MainActivity.onCreate` через `AppLanguage.apply()`
  (переопределение `updateConfiguration`, работающее на API 14 - 23), после чего
  активность перезапускается.
* **Каждый** видимый текст берётся из ресурса, включая названия поставщиков и
  примечания в списке источников сертификатов: `CertCatalog` читает их через
  `Context.getString()` при построении каталога. Поэтому каталог строится после
  `AppLanguage.apply()` - инициализатор поля выполнился бы до применения
  сохранённого языка и использовал бы язык системы.

Квалификаторы `values-zh-rCN` / `values-zh-rTW` / `values-zh` (а не
`b+zh+Hans` / `b+zh+Hant`) используются потому, что квалификаторы письменности
BCP 47 не поддерживаются до Android 5.0 (API 21).

Сам README переведён на те же шесть языков и перечисляет их в том же порядке в
переключателе сверху: `README.md` (упрощённый китайский, по умолчанию),
`README_zh_TW.md`, `README_en_US.md`, `README_pl_PL.md`, `README_ru_RU.md` и
`README_sv_SE.md`.

## Сборка

Требуется: JDK 17 (или 21) и Android SDK (build-tools 34, platform android-33).

```bash
./gradlew assembleDebug      # -> app/build/outputs/apk/debug/app-debug.apk
```

`gradlew` / `gradlew.bat` сами находят подходящий JDK. Встроенный в Gradle 8.7
компилятор Groovy не читает файлы классов более нового JDK, поэтому сценарий
сборки, в котором упоминается любой тип JDK - достаточно Boolean из
`buildFeatures { buildConfig true }` - падает с "Unsupported class file major
version 70"; машина, где `java` по умолчанию это JDK 26, именно такая. Поэтому
обёртка ищет сначала 17, а затем 21 в обычных местах (`/usr/libexec/java_home` в
macOS, Homebrew, `/usr/lib/jvm` в дистрибутивах Linux, JDK из Android Studio,
обычные папки установки в Windows) и указывает на найденное `JAVA_HOME`.
`JAVA_HOME`, уже указывающий на JDK одной из этих версий, не трогается, поэтому
осознанный выбор всегда сохраняется. Если ничего не найдено, обёртка сообщает об
этом, и решением будет установить JDK 17 или указать его в `JAVA_HOME`.

Эти два блока - один в `gradlew`, другой в начале `gradlew.bat` - для задачи
`wrapper` в Gradle невидимы, поэтому повторная генерация обёртки их выбрасывает.
После этого запустите `./build-prep.sh` (в Windows `build-prep.bat`), чтобы
вернуть их; `./build-prep.sh --check` только сообщает и ничего не меняет, чего и
хочет CI. Сами блоки лежат в `tools/gradlew-jdk17.sh` и `tools/gradlew-jdk17.bat`,
так что оба сценария делят одну копию.

Окно «О программе» (меню на верхней панели -> О программе) под текстом перечисляет
имя и номер версии, имя пакета, а также время и тип сборки (debug / release),
чтобы в отчёте об ошибке можно было назвать конкретную сборку. Время сборки
записывается в `BuildConfig.BUILD_DATE` файлом `build.gradle` на этапе
конфигурации, поэтому это момент сборки, а не установки; цена - один и тот же
коммит больше не даёт побайтово одинаковый APK.

## Ограничения

* Запись в `/system/etc/security/cacerts` требует root. Без root используйте
  режим пользовательского хранилища.
* Удаление из системного хранилища тоже требует root. В пользовательском
  хранилище его требует только один из трёх способов: он читает файлы напрямую,
  потому что в хранилище нет API для удаления сертификатов. Остальным двум root
  не нужен вовсе — ручной проход по списку в настройках и служба
  автоподтверждения, которая делает то же самое сама. Вторая проходит по экрану
  настроек той версии, на которой работает, поэтому устройство с другим экраном
  остаётся за ручным проходом.
* Службе автоподтверждения нужен Android 4.1 или новее; в Android 4.0 каждое окно
  установки в пользовательское хранилище приходится подтверждать вручную.
* Приложения, которые закрепляют сертификаты или имеют собственное хранилище
  доверия, этим не затрагиваются.
